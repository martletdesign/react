# Immutable-release documentation checkpoints — disabled candidate

This adapter prepares and verifies a `documentation-checkpoint.json` asset. It does not create, publish, change, or delete a GitHub Release and is **not wired into tag publication**. The existing release jobs and `verify-docs-published.mjs` gate stay disabled. This is a reviewable component, not a complete production authority.

GitHub documents that, when immutable releases are enabled, a published release's assets cannot be modified or deleted and its associated tag cannot move or be deleted **while that release exists**. GitHub creates a release attestation covering the tag and assets. The documented verification commands are `gh release verify` and `gh release verify-asset`. Sources: [immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases) and [release integrity verification](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/verify-release-integrity).

An authorized administrator can delete the entire immutable release and then delete its tag; the tag name cannot be reused. Immutable releases do not prove which release is newest after deletion, prevent repository compromise, or serve an HTML site at historical URLs. GitHub release title, notes, latest status and prerelease flag remain mutable. Keep protected tag rules, authorized main history and an independently durable, anti-rollback head checkpoint; alert on missing release or tag. Never fall back silently to an older release after a 404, deletion, API error, missing asset or failed signature.

## Checkpoint schema

The asset is UTF-8 JSON with `schemaVersion: 1`, `family`, `framework: "react"`, framework `version`, `source: {repository,tag,commit}`, `manifestSha256`, `catalogSha256`, `promotionSha256`, and `previous` equal to `null` for a reviewed bootstrap or `{tag,sha256}` for the preceding checkpoint. Digests are lowercase SHA-256. `source.repository` must be the dedicated React repository and the version must match its tag. A prerelease records the unchanged stable promotion digest, or `null` only when no stable release exists; it never promotes itself. A stable release records its own promotion digest. Every non-null hash must be independently verified. This record contains no credentials or package data.

`checkpoint-cli.mjs prepare OUTPUT INPUT_JSON EXPECTED_COMMIT` validates and creates a local file with exclusive creation; it does not contact GitHub. Set `GITHUB_REPOSITORY` and `RELEASE_TAG`. The caller is responsible for checking that the input hashes match the independently verified remote archive and catalog. Use the exact asset basename `documentation-checkpoint.json`.

`checkpoint-cli.mjs verify ASSET_PATH PINNED_SHA256 EXPECTED_COMMIT` validates the explicitly pinned bytes and identity, requires the GitHub API to report a published immutable release with exactly one matching asset and digest, calls both `gh release verify` and `gh release verify-asset` for the exact repository and tag, verifies origin and the remote/local tag object, and requires the supplied source commit on fetched `main` first-parent history. A protected main ruleset and release-tag rules are separate administrator requirements; ancestry is not proof of review. It never logs credentials. A recent authenticated `gh` with both verify subcommands is required. The current development environment's gh 2.46 does not provide them, so live attestation verification has **not** been run.

The `verifyCheckpointChain` library function verifies every supplied asset and parent link, requires an independently supplied expected head digest and anchor digest, and rejects absent, changed or reordered entries. A historic anchor alone cannot detect rollback to that anchor; the expected current head must be stored independently with rollback protection. The code does not yet provision such a store or automatically select the newest release. Do not take both pins from the R2 gateway or an unauthenticated latest pointer. The separate `checkpoint-state-cli.mjs` integrates those checks with read-only archive, catalog and promotion verification, as described below.

## Release ordering and interrupted recovery

1. Verify the previous checkpoint chain and independently pinned latest head, then build and verify the new local and remote archive without changing old snapshots. Use conditional catalog and promotion operations. The reviewed tag remains the routine release authorization.
2. Publish the npm artifact only under a separately authorized, activated workflow and verify registry bytes and provenance. This draft does not implement that activation.
3. Prepare the checkpoint bytes locally. For a future approved immutable-release workflow, create a draft GitHub Release only after registry verification, attach the exact checkpoint asset, then publish the draft with immutable releases enabled. Draft release contents are **not** immutable. Verify the resulting immutable release and local asset with both gh commands before recording the new off-bucket head.
4. If npm publication succeeded but release creation, asset upload, attestation verification or head recording failed, never run npm publish again. Verify the existing npm package and provenance, original tag, archive bytes and the exact checkpoint. If a published immutable release already exists, verify its attested asset matches exactly; if the release or asset differs, or the head is ambiguous, stop for review. An existing published immutable release cannot be repaired by replacing or adding its checkpoint; use an explicitly reviewed recovery approach that preserves release history. If an unpublished draft exists, inspect its complete contents before any separately authorized repair. Retrying local verification is read-only and safe.

No live release, asset upload, ruleset, npm trust, R2 bucket or DNS change is performed by this candidate. The application workflow must remain fail-closed until the anti-rollback authority, immutable-release settings, permissions, live GitHub attestation verification, R2 isolation, remote bytes, promotion verification, historical serving and end-to-end recovery have all been verified under separate authorization.

## Integrated read-only state verification

`checkpoint-state-cli.mjs ASSET CHECKPOINT_SHA COMMIT CATALOG_HEAD PROMOTION_HEAD ARCHIVE_HTTPS_BASE` verifies the pinned immutable-release asset and source, checks every archived file against its signed checkpoint manifest, validates the complete catalog history against the separately pinned current catalog head, and follows promotion history to the separately pinned current promotion head. Pass the literal `none` for the promotion head only when no supported stable release exists and no promotion pointer exists. Stable checkpoints must match their own promotion and catalog; prerelease checkpoints must preserve the prior stable promotion or establish its absence. Every promotion references a catalog in the pinned chain. The archive origin supports a path prefix such as `/preview`. Set `GITHUB_REPOSITORY` and `RELEASE_TAG`. The command is read-only and rejects missing, corrupt, substituted, stale or unavailable state. It cannot establish the current head pins: those must come from an independently protected anti-rollback authority.

If an interrupted transition leaves `/docs/latest.json` unavailable or the archive incomplete, the verifier stops rather than selecting an older value. Repair remains an authorized operator action using the original exact bytes and expected CAS parents; retry this verifier after repair. It does not repair or publish npm packages, releases, archives or pointers. Local integration tests use a fake signed-release command runner and in-memory R2 implementation; they are not live attestation or Cloudflare evidence.

React adaptation of the shared Astro checkpoint proposal in [Astro #15](https://github.com/martletdesign/astro/pull/15); tests below use simulated attestation and do not constitute live GitHub verification.
